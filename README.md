# StudioLab: отдельный воркер говорящих клипов

Картинка и готовый голос → MP4 с движением и речью, 25 fps. Это самостоятельный второй Vast serverless worker:
`worker.py` и `requirements.txt` должны находиться в корне будущего репозитория развёртывания. Импортов из соседнего
`comfy-worker/` нет. Его транспорт, очередь, идемпотентность, TTL, экзамен, диагностический журнал и самоудаление перенесены сюда.
Студия и существующий воркер не изменены. Commit/push не выполнялись.

Движок — LongCat-Video-Avatar 1.6, bf16: один постоянный процесс обслуживает последовательные задания без повторной загрузки моделей.
Голос приходит готовым файлом; синтеза речи нет. В revision 2 добавлены диалог двух людей, FA3 на Hopper, компиляция DiT
и удержание последних кадров. Параметры и ответы: [revision 2](avatar-contract-r2.md), основа — [revision 1](avatar-contract.md).

## Жизнь машины

1. Родитель очищает файл маркеров, запускает 30-минутный watchdog и **сначала прокси**, затем экзамен и установку.
2. `AVATAR_STAGE exam`: RAM, свободный диск, скорость записи, загрузки и отдачи. Источник измерения скачивания — самый большой
   отсутствующий файл манифеста; байтовые диапазоны читаются параллельно, проба не сохраняется. В разработке этот экзамен не запускался.
   RAM < 110 GiB, свободный диск < 180 GiB или оценка загрузки > 1200 с → отказ до установки. Неизмеренный показатель не считается нулём.
   `AVATAR_EXAM=0` отключает отказы; пороги можно переопределить в шаблоне. `AVATAR_EXAM {…}` либо `AVATAR_EXAM_FAILED <reason> {…}`
   содержит только публичные факты машины. Они вместе с `boot_s` приходят в каждом state.
3. `AVATAR_STAGE install`: системные ffmpeg/ffprobe и libsndfile1, проверенный checkout, Python 3.10 venv и закреплённый стек.
4. `AVATAR_STAGE download`: 44 файла, **63 163 373 768 байт** (63,16 GB, около 58,83 GiB). Части скачиваются диапазонами с
   возобновлением, проверкой ответа, размера и SHA-256; установка готового файла атомарна. Уже готовые файлы тоже проверяются по хешу.
5. `AVATAR_STAGE server`: локальный API проверяет доступность GPU и готовность. Только после health появляется `AVATAR_READY`;
   следом создаётся ready-файл и снимается watchdog. Benchmark вызывает state для специальной failed-записи, ничего не генерирует.
6. SDK допускает маршрутизацию только после READY. Все четыре session handler (`create`, `get`, `end`, `health`), включая внутреннее
   webhook-приложение, возвращают 404 `{"error":"unknown"}` без чтения тела. DEBUG SDK отключён, размер публичного envelope ограничен.

Неустранимый сбой загрузки/установки, выход дочернего сервиса или watchdog даёт `AVATAR_FATAL <stage> <Class>` без текста исключения.
Ошибка необязательной сборки FA3 даёт `AVATAR_FA3 off <причина>` и оставляет FA2. Падение движка после готовности вызывает его перезапуск;
теряется только выполняемое задание, два ожидающих сохраняются.
При `AVATAR_FATAL` родитель останавливает модельный сервис, оставляет прокси ещё на 15 с для метрик SDK и вызывает самоудаление.
Удаление повторяется до 2xx/404: задержки 1, 2, 4, 8…60 с, затем по 60 с; ошибки сети и 401/403/429/5xx не считаются успехом.
Отсутствие контейнерного ключа/ID и явное отключение отмечаются фиксированным маркером.

Ключ удаления остаётся только у родителя. Установщик, модельный сервер, ffprobe/ffmpeg и движок получают окружение без ключей,
токенов, паролей и секретов; прокси получает только необходимые токены SDK. Окружение не печатается и `.env` не читается.
Значения credentials редактируются до вывода в stdout и журнал, даже при разрыве между блоками чтения.
Диагностический журнал ограничен четырьмя файлами по 5 MiB. Файл маркеров отделён от произвольного вывода библиотек.

Очередь: одно выполняемое и два ожидающих задания. Их lease, текущий HTTP-запрос и передача MP4 защищают от idle-удаления.
Health не продлевает простой. После 540 с настоящего простоя API помечает себя retiring и просит родителя удалить машину.
Повторы request и fingerprint проверяются после декодирования повторно, непосредственно перед регистрацией: конкурентные повторы
получают один id. Проверка картинки и аудио выполняется вне event loop, не более двух операций одновременно.
Временные входы проверки находятся внутри частного каталога заданий; отклонённые запросы их удаляют.

Готовые и failed-записи, fingerprint и MP4 живут 3600 с после завершения; queued/running не истекают. Уборка идёт каждые 15 с
и перед запросом записи. Передача, начатая до TTL, может закончиться позже. Повторная загрузка разрешена; конкурирующая получает 404,
оборванная освобождает файл. Range игнорируется: ответ — весь MP4, `video/mp4`, точный Content-Length.
Память очереди теряется при перезапуске; машина может удалиться по простою раньше TTL, если студия перестала опрашивать её.

## Стек и выполнение задания

Код [LongCat-Video](https://github.com/meituan-longcat/LongCat-Video/tree/58eb336edc5c8c63389838727e40b8c18434e54e)
закреплён на `58eb336edc5c8c63389838727e40b8c18434e54e`; installer проверяет HEAD и отсутствие изменений отслеживаемых файлов.
`avatar_engine.py` выведен из сохранённых [single demo](evidence/demo.py) и [multi-person demo](evidence/upstream-multi-demo.py)
того же commit, с [MIT-лицензией](evidence/LICENSE).

- Python 3.10 в отдельном `/workspace/studiolab-avatar/venv-py310`.
- torch 2.6.0+cu124, torchvision 0.21.0+cu124, torchaudio 2.6.0+cu124 из PyTorch cu124 index.
- FA2: готовый flash-attn 2.7.4.post1 `cu12torch2.6cxx11abiFALSE-cp310-cp310-linux_x86_64.whl`.
- FA3: `flash-attention@060c9188beec3a8b62b33a3bfa6d5d2d44975fab` (v2.8.3), сборка `hopper/setup.py install` в тот же venv
  после torch. Флаги пробного скрипта: только bf16 inference и head dim 128; отключены backward, split, pagedkv, appendkv,
  local, softcap, fp16, fp8 и head dim 64/96/192/256. `MAX_JOBS = max(1, min(64, cores, floor((available_GiB − 8) / 4)))`.
  PATH сборки содержит именно worker venv для ninja; окружение SDK предварительно очищается.
- FA3 выбирается только при compute capability 9.x у всех участвующих GPU и успешном импорте. Иначе — FA2.
  Совместимость возвращаемых значений `(out, None)` добавляется в памяти до импорта LongCat, установленные файлы не меняются.
  DiT получает `enable_flashattn3=True, enable_flashattn2=False` через `from_pretrained`: закреплённый класс наследует
  Diffusers ModelMixin/ConfigMixin и регистрирует оба параметра в `__init__`. Скачанный config не изменяется.
- DiT компилируется по upstream по блокам: cache limits 128/1024, fullgraph=False, dynamic=False,
  triton.cudagraphs=False, epilogue_fusion=False, emulate_precision_casts=True. Кеши Inductor и Triton лежат в закрытом
  каталоге движка, живут между заданиями и не удаляются вместе с входами первого клипа.
- Оба requirements закреплённого upstream, без torch/torchvision/torchaudio, flash-attn, libsndfile1, tritonserverclient, streamlit и openai.
  Сохранены исходные версии, в частности numpy 1.26.4, transformers 4.41.0, diffusers 0.35.1, onnxruntime-gpu 1.20.2.
- huggingface_hub **0.35.3**; accelerate **1.10.1** добавлен для `low_cpu_mem_usage=True` при загрузке UMT5, VAE и DiT,
  чтобы уменьшить пиковую RAM. Фактическая экономия на GPU-машине ещё не измерена.
- LD_LIBRARY_PATH движка начинается с `venv-py310/lib/python3.10/site-packages/nvidia/cudnn/lib`, затем cublas, CUDA runtime,
  torch/lib и прежние пути. Разделитель вокала остаётся на CPU: его CUDA provider несовместим с cuDNN этой сборки.

Файлы перечислены в [model-manifest.json](model-manifest.json): каждый имеет repository, полный revision, source_path,
локальный path, size и sha256. Деревья Hub сохранены в `evidence/`; у LFS-файлов SHA-256 взят из oid.
Для небольших JSON/TXT прочитан текстовый Git blob, проверен его SHA-1 oid и вычислен SHA-256; веса и LFS-объекты не скачивались.
`build_manifest.py` воспроизводит манифест по этим снимкам, читая только небольшие текстовые файлы.
Каталоги весов соседние: `weights/LongCat-Video/` и `weights/LongCat-Video-Avatar-1.6/`, как ожидает upstream.
Нет int8, fp32-дублей Whisper, Flax или лишних diffusion-весов базового LongCat-Video.

После загрузки весов сервер один раз запускает
`torchrun --standalone --nproc_per_node=G avatar_engine.py --inbox <private-dir> --context_parallel_size=G`.
Все ранги загружают модели, проходят барьер; rank 0 атомарно пишет ready.json. Только затем сервер становится healthy
и родитель пишет `AVATAR_READY`. Пока идёт перезагрузка, health недоступен, новые задания получают busy.
Сервер атомарно публикует одно задание в inbox. Rank 0 читает его и рассылает всем рангам через отдельную gloo-группу
с таймаутом 7 суток. NCCL и его context-parallel подгруппы имеют таймаут 1 час. В простое rank 0 спит по 250 мс,
остальные блокируются на gloo; NCCL-операция не остаётся ждать следующего задания.
G — число видимых GPU, округлённое вниз до 1, 2, 4 или 8; при G > 2 выставляется `LONGCAT_A2A_WORKSPACE=1`.
Выбран `avatar-v1.6`: внутренний путь v1.5, без loudness normalization; 8 distilled шагов, DMD/OPSD из loraA/loraB,
`mix_steps=4`, `mix_alpha=1.0`, `ref_img_index=10`, `mask_frame_range=0`, исходный negative prompt upstream, seed и prompt задания.
Сначала ai2v, затем AVC-продолжения с 13 conditioning frames. JSON прогресса атомарно пишет только rank 0 после каждого сегмента.

Финальные кадры кодируются **один раз**, обрезаются до числа кадров исходного аудио или дополняются последним кадром, максимум на 3 кадра.
Затем отдельный ffmpeg mux добавляет **исходный** голос с AAC. Stem разделителя используется только для embeddings.
В диалоге две дорожки идут одновременно с t=0; короткая дополняется тишиной. Эмбеддинги и маски двух людей передаются и в первый
сегмент, и в продолжения. Дробные boxes переводятся в пиксельный `[y0, x0, y1, x1]`; без boxes используются отступы upstream
в левой/правой половинах. Третья маска — фон. Поля others в контракте нет, дополнительный фоновой аудиоэмбеддинг не создаётся,
как в upstream при `use_background_silent_audio=False`. Выходной звук — сумма двух оригиналов с ограничителем пиков 0,95, затем AAC.
H.264, yuv420p, CRF 16. `save_video_ffmpeg` upstream не используется. Входы и временные media удаляются после подтверждения
завершения всеми рангами; сам движок остаётся загруженным.

Лимит задания — 3600 с после отправки загруженному движку, включая подготовку аудио, компиляцию новых форм и mux.
На таймауте, отмене или падении уничтожается вся группа процессов и проверяется отсутствие живых дочерних процессов.
После таймаута/падения сервер запускает новую группу и загружает модели; ожидающие задания продолжаются после ready.json.
Если остановку подтвердить не удалось, новый start получает busy. Загрузка моделей ограничена 1200 с за попытку.
На Windows локальные тесты проверяют дерево процессов; Linux-развёртывание использует process group.

## Оценки и границы проверки

При 100–200 MiB/s сами файлы займут примерно 5–10 минут. Ориентир холодного старта r2 — **12–24 минуты**,
включая экзамен, установку, сборку FA3 и загрузку моделей; это оценка, не измеренный SLA. Пробная сборка FA3 заняла **103 с**
при 224 ядрах и MAX_JOBS=64. На машине с меньшей RAM/числом ядер она может занять дольше. Загрузка моделей порядка 60–120 с
теперь оплачивается временем при старте и восстановлении, а не на каждом задании. Первый вызов новых форм DiT дополнительно
компилируется уже в задании. Watchdog всего старта — 30 минут.

Замеры владельца 17.11.2026, **секунд на шаг**, 8 шагов на сегмент:

| Режим | 2×H100, 480p | 2×H100, 720p | 1×H100, 720p |
| --- | ---: | ---: | ---: |
| FA2 | 3,4 | 12,3 | 24,6 |
| FA3 | 2,9 | — | 18,1 |
| FA3 + compiled DiT | — | 6,8 (первый сегмент) | 12,5 |
| Диалог, FA3 | 3,23 (около +11%) | — | — |

Ранее продолжения с новыми формами давали 8,5–12 с/шаг; постоянный движок сохраняет кеш между заданиями, но выигрыш именно этой
реализации ещё не измерен. **10,14 с → три сегмента**, последний кадр удерживается на недостающий хвост.
Длинное 720p на одном H100 может превысить час.

Проверка из этого каталога: `D:/SuperAI-data/work/venv-workers/Scripts/python.exe -m pytest -q`.
Зависимости — `requirements-test.txt`, ffmpeg/ffprobe в PATH; CUDA, torch и модели тестам не нужны.
Loopback-only guard запрещает внешний сетевой доступ тестов. Используются синтетические изображения, звук, credentials и отдельный
fake engine, создающий настоящий MP4. Проверяются транспорт реального SDK 1.8.3, очередь/TTL, процессное дерево, медиадорожки,
манифест, план установки, redaction и retries самоудаления. Временные тестовые файлы создаются только в `.tmp/` этого каталога.

**В этой ревизии не проверено на GPU:** сборка FA3 на выбранном образе, реальные RAM/VRAM и холодный старт r2,
NCCL/gloo/context parallel, кеш компиляции после нескольких заданий, качество диалога и синхронизация речи, 60-секундные ролики.
Vast не вызывался, GPU-код не запускался, веса не скачивались. Независимый Opus-review должен выполнить conductor:
Opus недоступен в инструментах этого исполнителя. Оставшиеся проверки перечислены в [needs.json](needs.json).

При повторном запуске экзамен вычитает из порога свободного места объём, уже занятый файлами работника. Для заданий и кеша должно оставаться хотя бы 30 ГиБ.

При сбое задания маркер `AVATAR_JOB_FAILED` показывает последний этап, долю выполнения и краткую причину. В ответе о состоянии задания поле `error` содержит эту причину. Маркер `AVATAR_HEALTH` при первом опросе и смене состояния показывает готовность или причину недоступности (`engine` либо `retiring`).
